## 「はじめに」
本リポジトリは就職活動のポートフォリオ用として現行の自宅インフラ環境を構成する際に使用しているサンプルファイルを公開する目的で作成したものです。<br>
(技術スタック:Linux[Debian],Kubernetes[K3S],Docker,MariaDB & MaxScale,ISC Kea DHCP,CoreDNS)<br>
<br>

## 「概要」
本ポートフォリオは、自宅で稼働している従来型のベアメタル環境のサーバーからKubernetes系(K3S)のクラスタ環境のサーバー(マルチノード環境)に移行することを目的としたものを題材にしたものであり、現時点においても移行作業中となっています。<br>
そのため、全体の進捗から一部構築完了した部分を掲載いたします。<br>
<br>
## 「目標」
現在稼働している従来のベアメタル環境からベアメタルコンテナ環境(Kubernetes)に移行しつつ、クラスタを構築する。<br>
将来は可能な限りHA(高可用性)を実現させつつ、CI/CD環境の構築と整備を行い、管理しやすい環境を構築しながら学習する。<br>
<br>
## 「移行動機」
当初は一台のメインサーバー(Raspberry Pi 4)のみでDHCPサーバー、キャッシュDNSサーバー、家庭内Webアプリのホスティング環境、自主制作の防犯カメラシステムの録画サーバーとしての機能を提供しており、随時稼働のサーバー(ファイルサーバー、VPNサーバー)も運用していました。しかし、現状の一台のサーバーだけでは、サービスがエラー等により停止した際に他の利用者IPアドレスを取得できなくなったり名前解決ができなくなることがあったこと、今までは定時に随時稼働のサブサーバーを遠隔起動させ、メインサーバーの設定ファイルや録画データのバックアップを行っていたが、経年劣化により故障したことと、そして、実際にKubernetesのクラスタを構築し、運用することで得られる経験と知見を得たいと思い、移行を行いました。<br>

## 「工夫した点」
従来のサーバーから新環境に移行する際に注力したポイントは、手持ちの部品と機材を組み合わせながら予算と消費電力、システムリソース消費を抑えつつ主要サーバーの冗長化を図った点です。<br>
予算面では手持ちの部品や機器("Raspberry Pi 4"を2台)と予算の約5000円で購入した素材を組み合わせて構築しました。将来的にいつでも一般的なx86環境への移行&スケールアップを行えるように"Raspberry Pi 4"をマウントできるマザーボード型のマウンターと独自の電源制御モジュールを制作しました。ちなみに予算の都合上、追加購入は見送りましたが、制作したマウンターには"Raspberry Pi 4"をさらに1台追加してスケールアウトできるようにするためのスペースを残しています。<br>
消費電力に関しては、"Raspberry Pi"(ARM)系をベースに構築することで、Kubernetesのマルチノード構成兼NASとして動作しても通常時の消費電力は最大でも50W未満に収まります。<br>
冗長化面では、DHCPサーバーもアクティブスタンバイ構成で自宅内DNSサーバー(CoreDNS)は元々ロードバランシングで運用するようにしました。<br>
<br>
なお、KubernetesのノードやDBサーバーにおいて、HAクラスタではなくアクティブスタンバイ構成で構築した理由は、現状では流用できるサーバー(Raspberry Pi 4)が2台しかなく、HAクラスタ環境を構築するには向いていないと判断し、マスターノード側もワーカーとして動作させつつスタンバイ側のDB、DHCPサーバーを配置し、ワーカーノードにはアクティブ側のDB、DHCPサーバーを配置するようにリソースを振り分けています。なお、その他のアプリケーションは全てワーカーノード上で動作するように振り分けています。<br>
MariaDBサーバーでは、非同期レプリケーション構成とMaxScaleプロキシを組み合わせて実現しています。<br>
当初は仮想マシン上で動作させることを考えましたが、オーバーヘッドによる性能低下でリソースの余裕がなくなると判断したため、今回はベアメタルコンテナ環境として構築しました。また、DNSサーバーにはBINDではなく軽量なCoreDNSを採用する、分散ストレージのLonghornと他のサーバーアプリケーションに対してリソース制限を設けるなどをしてシステムリソースの負担を軽減するといったことを行いました。<br>
<br>
## 「苦労した点」
初めてKubernetesのマニフェストファイルを作成する際、Docker Composeの設定ファイルとは書き方や考え方が違うだけでなく、設定ファイルや認証ファイルの保管場所(ComfigMap、Secret)やコンテナのネットワークの公開方法(Service)、を定義する際に将来運用、スケールアウト等をしやすくできるように考慮する書き方をしないといけない点に苦労しました。<br>
また、MariaDBを非同期レプリケーション(アクティブスタンバイ)構成でMaxScaleプロキシでロードバランシングを構築するのは初めてであったため、認証関連のトラブルに悩まされながらも、技術系コミュニティの記事を参考にしたり、英語のみのドキュメントに対しては翻訳して読んだり、回答を精査しながらではありますが、AI(Google Gemini)を活用して、学びながら構築しました。<br>
<br>
## 「今後の目標」
現時点では現行の構成にKubernetes系のクラスタ環境を追加したような構成になっていますが、随時既存サービスやソフトウェアのコンテナ化を進めていき、最終的には主要サービスやソフトウェアをKubernetes上で動作するように移行作業を続けていきます。<br>
また、現状では手動でコンテナをデプロイしている状況であるため、近い将来にはArgoCD等のCI/CD環境を導入し、自宅環境でのGitOps化を推進していく予定です。<br>
